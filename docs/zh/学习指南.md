# 学习指南：Revenue & Commission Operations Workbench（营收与佣金运营工作台）

> 这份指南写给刚接触编程、但有金融/数据分析背景的你。每个核心概念都按同一个顺序讲：
> **字面拆解 → 场景重演 → 简单版 → 进阶版**，复杂的再加 **对照组 / 痛点溯源**。
> 项目本身是**合成数据的独立作品集原型**，不是会计系统、不是任何雇主的系统，由 AI（Claude Code）协助构建。

---

## 0. 先用 60 秒看懂这个项目

**一句话**：它回答销售运营分析师每个月必须回答的六个问题——收到了多少现金、哪些能算佣金、每个销售该拿多少、数字为什么变了、为什么和工资系统记录的不一样、关账后怎么防止历史被改写。

**怎么跑起来（Mac）**
1. 第一次：在「终端」里执行（只需一次）：
   ```bash
   cd 项目文件夹
   python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
   ```
2. 以后每次：在 Finder 里**双击 `launch_demo.command`**，浏览器会打开 http://127.0.0.1:5057 。
   它**不会**删除你之前的操作；只有第一次（数据库文件不存在时）才会自动放入示例数据。
3. 想从头再演示一次：双击 `reset_demo.command`，输入 `RESET` 回车（会先自动备份旧数据库到 `instance/backups/`）。
4. 什么都装不了？直接 `python3 -m rcw demo`（不需要安装任何包），它会把整个故事跑一遍并导出报表到 `out/demo/`。
5. 连电脑都开不了服务？打开 `docs/presentation/walkthrough.html`——这是**演示回放**（录制好的截图和数字），不是实时系统。

## 1. 四种“钱”：签约额、发票、回款、佣金

**字面拆解**
- *Booking（签约额/订单额）*：`contracts.csv` 里的 `booked_amount` 一列——客户签了合同，写在合同上的总价。
- *Invoice（发票）*：公司发给客户的账单。本项目**不导入发票**，回款行里的 `invoice_ref` 只是备注。
- *Cash collected（回款）*：`cash_events.csv` 里 `event_type = COLLECTION` 的行——钱真正到了公司账户。
- *Commission（佣金）*：程序算出来的“应付给销售的钱”，由若干“计算行”（line）组成。

**场景重演**
周一上午 9 点，分析师坐在笔记本前，打开工作台的「May 2026」页面。屏幕顶部一排小方块：`Bookings signed 0.00`、`Cash collected 11,000.00`、`Refunds 1,000.00`、`Commission earned 590.00`……她用鼠标指着说：“这个月没签新合同，但收到了 1.1 万现金，所以有佣金。”整个过程 10 秒。

**简单版**：签约像“订了外卖”，发票像“店家给你账单”，回款像“钱真的付了”，佣金像“骑手按实际送达的单子拿提成”。本项目只在“钱真的付了”时给提成。

**进阶版**：按回款计佣（cash basis）的好处是最难被撤销、退款有明确对象；代价是回款周期长时销售拿钱慢。三种金额在页面上**永远分开显示、不相加**，也**都不是会计上的“确认收入”**（ASC 606 / IFRS 15 没有建模）。面试时常见的坑：把 bookings 当成收入，或把不同币种直接加总——本项目两种币种（SGD/USD）永远分开，没有汇率。

## 2. 分成（Credit split）与“多出来的一分钱”

**字面拆解**：`splits.csv` 每行 = 合同号 + 销售号 + 百分比。一张合同的所有行加起来必须**正好 100.00%**。

**场景重演**：USD 12,345.67 的回款，Cedar 60% / Delta 40%。
12,345.67 × 60% = 7,407.402 ，× 40% = 4,938.268。钱只能精确到分：先各自向下取整 → 7,407.40 + 4,938.26 = 12,345.66，**少了 1 分**。谁拿？看小数部分：0.2 分 vs 0.8 分 → 0.8 更大 → 给 Delta。结果 7,407.40 / 4,938.27，合计正好 12,345.67。

**简单版**：几个人分一盒饼干，分不匀的最后几块，给“差得最多”的人。

**进阶版**：这叫**最大余数法（largest remainder）**。平局（比如 0.01 美元 50/50）按销售编号字母顺序给小的那位——规则写死，所以**文件顺序、导入顺序都不影响结果**。控制检查每次都验证“分给销售的分 = 收到的分”。坑：如果每人各自四舍五入，50/50 分 0.01 会变成 0.01 + 0.01 = 0.02，凭空多出一分钱。

## 3. 边际加速器（Marginal accelerator）

**字面拆解**：`plans.csv` 里的 `threshold_amount = 10000.00`、`base_rate_pct = 5.00`、`accelerator_rate_pct = 8.00`。每个销售、每个月、每种币种各有一个“阶梯”。

**场景重演**：Aurora 4 月 6 日回款 10,000 → 全部在门槛内 → 5% = 500；4 月 20 日又回款 2,000 → 门槛已满 → 全部 8% = 160。4 月合计 660。页面“证据”卡片上写着：`attainment before 10,000.00 → below threshold 0 × 5% → above threshold 2,000.00 × 8% = 160.00`。

**简单版**：像个人所得税的累进税率——只有**超过**门槛的那部分用高税率，前面的钱不重算。

**进阶版**
- *对照组*：“追溯式”加速器是“一旦过线，全月都按 8%”，会让之前已算好的行全部改变，还会出现过线前后差一块钱、提成差几百的“悬崖”。边际式没有悬崖，每行独立可解释。
- 阶梯计的是**毛回款**（正的回款），退款不会“还回”额度——否则一笔退款会悄悄改变别的订单的档位。
- 同一笔回款可以“跨线”：9,000 之后再来 3,000 → 1,000 按 5%，2,000 按 8%（测试 HC-04）。
- 计划版本按“回款日期”生效，并且必须从某月 1 日开始：4 月 30 日的钱用 v1（8%），5 月 1 日的钱用 v2（9%），而且 5 月阶梯重新从 0 开始（HC-11）。

## 4. 退款追回（Clawback）与“累计冲回”

**字面拆解**：退款是 `cash_events.csv` 中 `event_type = REFUND` 的一行，`original_event_id` 指向它退的那笔回款。

**场景重演**：5 月 12 日，客户退回 4 月那笔 2,000 中的 1,000。此时 5 月计划已改成 9%。工作台在 Aurora 的 5 月账单上生成一行 `Refund clawback −80.00`，证据页写着：原始佣金 E = 160.00，回款 x = 2,000，冲回 = 160 × 1,000 ÷ 2,000 = 80。

**简单版**：你按 8% 拿过的提成，退一半货就按**当时的 8%** 退一半提成，不会因为现在涨到 9% 就多扣。

**进阶版**：累计公式：退款累计达到 R 时，总冲回 = `四舍五入(E × R ÷ x)`，每次只冲“这次累计 − 上次累计”。
- *为什么*：如果每次退款各自四舍五入，10 分钱的佣金分三次退（0.67 + 0.67 + 0.66）会算成 3 + 3 + 3 = 9 分，少冲 1 分；累计法是 3 + 4 + 3 = **正好 10 分**（测试 HC-08）。
- 冲回的是**存下来的原始行**，不是按今天的规则重算，所以就算中途换了计划版本也不会变（HC-02）。
- 超额退款（累计退款 > 原回款）在导入时就被拦下（`OVER_REFUND`）。

## 5. 关账（Period close）与快照（Snapshot）

**字面拆解**：关账 = 点击「Close 2026-04」按钮。程序把这个月的全部计算行、输入数据、规则版本、控制检查写成一个 JSON 快照，算出 SHA-256 指纹，并在数据库里用触发器禁止修改。

**场景重演**：analyst-1 点「Submit for review」；她想自己点「Close」，系统拒绝（`SAME_ACTOR`）。右上角把「Acting as」切成 manager-1，再点 Close，绿色提示：`Closed. Snapshot SHA-256 e408…`。之后导出的 4 月报表，无论后来导入什么、改什么计划，**每个字节都一样**。

**简单版**：关账像给账本拍照并盖章封存，以后只能在新的一页写“更正”，不能涂改旧页。

**进阶版**
- *审阅的就是冻结的*：关账时程序会**重新计算一遍**，与“提交审阅时的那次计算”逐项比较（计算行、搁置项、排除项、合计、控制检查、KPI、输入数据）。任何一项不同 → 拒绝（`STALE_REVIEW`），要求重算重审。连“只导入了一张新签约合同、佣金一分没变”也会触发，因为签约额 KPI 会被冻结进快照（这是外部审阅者发现的缺陷 R-2）。
- 必须按月份顺序关账；月份没过完不能关。
- *诚实的局限*：“preparer ≠ reviewer”只是比较两个**标签**，不是登录认证；触发器能防程序误改，但拥有数据库文件的人仍能改文件。

## 6. 迟到数据（Late data）：不重开旧月份

**字面拆解**：日期属于已关账月份、但关账后才导入的回款/退款。

**场景重演**：6 月 4 日，银行对账单才送来一笔 4 月 29 日的 1,500 美元回款。4 月已关账。工作台在 5 月页面顶部显示红色搁置：`LATE_EVENT_PENDING`，「Submit」按钮是灰的。经理在输入框写原因“Bank confirmed receipt on 29 Apr…”，点「Post as prior-period adjustment in 2026-05」，重算后 Cedar 的 5 月出现一行 `Late cash (prior-period adjustment) 120.00`。

**简单版**：发现上个月漏记一笔，不去撕掉上个月的账页，而是在这个月写一行“补记上月”，并注明原因。

**进阶版**：这笔迟到回款按 **4 月冻结的阶梯**接着往后排（4 月已达 12,407.40，已超门槛），并用 **4 月的计划版本**（8%，不是 5 月的 9%）：1,500 × 8% = 120。这样已冻结的旧行一行都不动。也可以选择“排除”（同样要写原因）。决定一经记录不可修改，全部进入审计日志。

## 7. 差异调查（Variance case）

**字面拆解**：`recorded_payouts.csv` 是（合成的）工资系统记录。差异 = 记录值 − 预期值，按“月份 × 销售 × 币种”。

**场景重演**：Variance 页面，Aurora 5 月：预期 510.00，工资系统记录 590.00，差异 +80.00。点进 VC-0002，“建议解释”写着：`MISSED_CLAWBACK — 差异正好等于退款冲回行 −80.00 的相反数`。分析师选原因代码、写备注、改状态为 RESOLVED。页面醒目提示：**Resolved ≠ corrected ≠ paid**。

**简单版**：对账时发现两边数字不同，先找原因、记下来；“找到原因”不等于“钱已经退回来了”。

**进阶版**：案例编号、负责人、备注在每次刷新后都保留；如果差异金额变了，已解决的案例会自动重新打开（REOPENED）；差异归零则变为 CLEARED。建议是**确定性匹配**（差异是否正好等于某一行、某类行的合计、或“只按基础费率支付”的差额），只是提示，不是结论。

## 8. 幂等（Idempotency）与隔离区（Quarantine）

**字面拆解**：每个上传文件都算 SHA-256 指纹；每行有“自然键”（如 event_id）。

**场景重演**：同事把同一个 CSV 改名为 `april_final_v2.csv` 又上传一次——页面显示 `Duplicate of #6`，什么都没导入。另一行金额写成了 `1,250.00`（带千分位逗号）——这行进入 Quarantine 页面，原因 `AMOUNT_FORMAT`，其余正常的行照常导入，批次页面显示“读取 = 接受 + 重复 + 隔离”，金额也对得上。

**简单版**：仓库收货时按“条码”而不是“箱子上写的名字”判断是否已收过；有问题的货放到隔离区，不混进库存，也不偷偷扔掉。

**进阶版**：
- *对照组*：没有幂等 → 同一文件导两次，佣金翻倍；有幂等 → 第二次是有记录的“空操作”。
- 同一编号但内容不同 → 隔离为 `CONFLICT_EXISTING`，**原有数据绝不被覆盖**。
- 严格模式（strict）= 有一行错就整份文件都不导入（原子性）；隔离模式 = 好的行进来、坏的行带原因留下，并有控制合计，**绝不“悄悄部分成功”**。
- 隔离区里如果还有本月的现金行，本月不能关账，除非有人写原因“驳回”，或者之后导入了正确的同编号行（自动标记 SUPERSEDED）。

## 9. 为什么金额用“整数分”，不用小数（float）

**字面拆解**：数据库里所有金额列都叫 `*_minor`，存整数：12,345.67 存成 1234567。费率存“基点”：5% = 500。

**场景重演**：在 Python 里输入 `0.1 + 0.2`，屏幕显示 `0.30000000000000004`。用整数分：10 + 20 = 30，永远精确。

**简单版**：用“分”记账，就不会出现 0.1 + 0.2 ≠ 0.3 的尴尬。

**进阶版**：每行佣金只在最后四舍五入一次（half-up：0.5 进位），证据页会显示“精确值”和“舍入差”。解析金额时只接受 ASCII 数字：测试中发现 Python 的 `\d` 会把阿拉伯文数字“٣”当成 3（缺陷 D-001），已修复。

## 10. 一次 30 分钟的最小实验

1. `python3 -m rcw demo`（约 1 秒），打开 `out/demo/2026-04_statement.html`，找到 Cedar 的 692.59 是怎么来的。
2. 复制 `data/demo/stage1/06_cash_events.csv`，把某一行金额改成 `1,250.00`，在网页「Imports」里用 quarantine 模式上传，看隔离原因。
3. 把同一个文件改名后再传一次，看 `DUPLICATE_FILE`。
4. 在 April 提交审阅后，再导入一张 4 月签约的新合同，然后尝试关账——会看到 `STALE_REVIEW`，并在提示里看到 “other changed sections: kpis”。
5. 打开 `tests/expected/HAND_CALCULATIONS.md`，挑一个场景自己用计算器算一遍，再对照测试结果。

| 术语 | 一句话人话解释 | 现在需不需要懂 |
|---|---|---|
| Booking / Bookings signed | 合同上签下的金额，本项目不据此发佣金 | 需要 |
| Cash collected / Collection | 真正收到的钱，本项目的佣金基础 | 需要 |
| Refund / Clawback | 退给客户的钱 / 因此从销售佣金里扣回的钱 | 需要 |
| Credit split | 一张合同的业绩按百分比分给几个销售 | 需要 |
| Threshold / Accelerator | 门槛 / 超过门槛部分用的更高费率 | 需要 |
| Attainment | 本月累计计入阶梯的回款 | 需要 |
| Minor units / Basis points | 以“分”为单位的整数 / 万分之一（5% = 500 bps） | 需要 |
| Largest remainder | 分不匀的零头给小数部分最大的人 | 需要 |
| Period close / Snapshot | 月结关账 / 关账时封存的完整数据照片 | 需要 |
| SHA-256 | 一段数据的“指纹”，数据变一个字节指纹就变 | 知道用途即可 |
| Hold (blocking) | 搁置项：有它在，本月不能提交/关账 | 需要 |
| Prior-period adjustment | 在当前月补记属于以前月份的金额 | 需要 |
| Variance case | 预期支付与记录支付不一致的调查单 | 需要 |
| Idempotency | 同样的操作做两次，结果和做一次一样 | 需要 |
| Quarantine | 不合格数据的隔离区，带原因，不混入正式数据 | 需要 |
| CSRF / CSP | 网页安全机制，防止别的网站冒充你提交表单 / 限制页面能加载的脚本 | 暂时不需要 |
| Trigger (SQLite) | 数据库里的自动规则，这里用来禁止修改已冻结数据 | 知道用途即可 |
| Oracle (test) | 另写的一个简单“参考答案程序”，用来和主程序对答案 | 知道用途即可 |
| ASC 606 / IFRS 15 | 会计上“确认收入”的准则，本项目**没有**实现 | 知道边界即可 |
